# 数据库迁移安全

## 何时使用

- 新增/修改/删除表、列、索引、约束；
- 大表变更、数据回填、类型迁移；
- 需要计划回滚或评估上线窗口。

## 步骤

1. **先判断是否破坏兼容**：旧代码是否还能读写新 schema？新代码部署前 schema 是否已就绪？多实例滚动发布期间新旧版本会同时运行。
2. **使用 expand → migrate → contract 分阶段**：
   - expand：只做加法（加可空列、加新表、加索引），同时兼容新旧读写；
   - migrate：双写或读切换，回填历史数据，校验一致性；
   - contract：确认无旧代码后再删列/删表/加非空约束。
3. **评估锁与耗时**：
   - 明确数据库版本下每类 DDL 是否锁表、锁多久；
   - 大表加索引优先使用并发/在线建索引；
   - 加 `NOT NULL` 先可空 → 回填 → 加约束（或分段校验）；
   - 修改列类型、重写表会重建数据，必须单独评估；
   - 避免在业务高峰执行，设置 `lock_timeout` 和语句超时，失败可重试。
4. **数据回填**：分批提交，可断点续跑，幂等；监控进度、复制延迟和锁等待；不要一次更新全表。
5. **准备回滚**：写清回滚步骤和触发条件；删除类操作先保留备份/软删除；回滚脚本要实际演练，不能只写文档。
6. **发布顺序**：schema 先行 → 应用灰度 → 验证 → 清理旧逻辑 → 最终 contract。每一步都可暂停。
7. **验证一致性**：迁移前后行数、关键聚合、抽样对照；有唯一约束/外键时先检查存量脏数据。

## 反模式

- 在一条迁移里同时改 schema 和删旧列；
- 大表直接 `ALTER` 加默认值/改类型，造成长时间锁表；
- 回填脚本不可重入，失败一次后状态混乱；
- 没有备份就删列/删表；
- 假设"迁移瞬时完成"，没有超时和失败处理；
- 回滚方案只存在于口头描述。

## 示例

```text
目标：orders.status 改为枚举并加索引
1. expand：新增 nullable 的 status_new，写路径双写，旧列保留
2. backfill：按主键分批更新，记录进度，幂等
3. 校验：新旧列差异为 0，抽样业务查询一致
4. 切换：读走新列，观察一个发布周期
5. contract：并发建索引 → 加约束 → 停双写 → 删旧列
```

## 验证方式

- 在等价数据量的预发库执行并记录耗时、锁等待；
- 回滚脚本演练成功；
- 新旧版本并行期间读写均正常；
- 迁移前后数据一致性校验通过。
