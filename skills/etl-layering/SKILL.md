# ETL 分层与复用

## 什么时候用

- 设计新 ETL 脚本，不知道该分几层、CTE 怎么拆；
- 评审已有脚本，判断层级是否合理；
- 决定什么时候把 CTE 落成物理表；
- 评估重复扫描、长表/宽表、星型/雪花。

## 一、先分清两种分层

| 类型 | 例子 | 作用 |
|---|---|---|
| 数仓物理分层 | ODS → DWD → DWS → ADS | 跨脚本共享、血缘、权限、复用 |
| 脚本内 CTE 分层 | `p_ → b_ → f_/j_ → a_ → 输出` | 单个脚本内可读、可维护 |

- CTE 只在当前脚本有效；**跨脚本复用要落物理表**，不要把 CTE 当成数仓分层。
- 物理层职责：ODS 原样接入；DWD 清洗后的明细；DWS 按主题汇总；ADS 面向报表的结果。

```mermaid
flowchart LR
  ODS["ODS 原始"] --> DWD["DWD 明细"]
  DWD --> DWS["DWS 汇总"]
  DWS --> ADS["ADS 报表"]
```

## 二、脚本内每一层做什么

| 层 | 职责 | 不该做什么 |
|---|---|---|
| `p_` | 日期、月份、分区、开关等参数 | 不读业务表、不写业务口径 |
| `b_` | 一个源表一个 CTE；重命名、cast、轻清洗 | 不 join、不聚合 |
| `f_` | 过滤后的集合，供下游复用 | 只过滤一次也单独成层 |
| `j_` | join 后的明细；一次 join 一个 CTE | 一个 CTE 塞多表 join |
| `a_` | 一个指标一个 CTE；粒度等于输出粒度 | 混多个指标、多个粒度 |
| `o_` | 多目标输出或统一改名 | 每个脚本都写 |

关键规则：

- **不是每层都要用**。简单脚本 `p_ → b_ → a_` 就够。
- `f_` 只在过滤结果被 ≥2 处复用、或过滤逻辑复杂时才独立；否则写在 `b_`/`a_` 的 `WHERE` 里。
- `j_` 按**结果**命名（如 `j_overseas_company_ledger`），不按输入命名；多表 join 拆成多个 `j_`。
- `f_` 和 `j_` **按实际数据流排**，不要按前缀强行排序；可能是 `b_ → f_ → j_ → a_`，也可能是 `b_ → j_ → f_ → a_`。
- `o_` 只在写多个目标表、或最后统一改字段名时用；否则最终 `SELECT` 就是输出层。
- 主干控制在 3–5 层；单个 CTE 内嵌套不超过 2 层；超过就拆中间表。

## 三、什么时候把 CTE 升级成物理表

满足任一条，就不要再复制 CTE：

- 同一段逻辑被 **2 个以上脚本**使用；
- 单次扫描成本高，结果被多个下游重复读取；
- 需要独立测试、血缘、权限或 SLA；
- 多人维护同一个口径。

落哪一层：

| 内容 | 落到 |
|---|---|
| 清洗后的明细 | DWD |
| 按主题汇总/宽表 | DWS |
| 面向报表的最终结果 | ADS |

反模式：把同一段 `b_` 复制到 5 个脚本。短期省事，长期口径一定分叉。

## 四、性能与输出形态

- **多个 `a_` 读同一个 `b_`**：小数据没事；大数据先把 `b_` 落临时表，或一次扫描用 `SUM(CASE WHEN ...)` 算多个指标。
- **同一 CTE 被引用 ≥2 次**：部分引擎会重复扫描；大表先落临时表。
- **长表 vs 宽表**：
  - 长表 `category, plate, total, diff`：指标少、结构固定、加指标方便；
  - 宽表：指标单位/列不同、指标多、BI 要一行看全；
  - `a_` 区块到 20+ 时，考虑拆表或改宽表，不要继续堆 `UNION ALL`。
- 先过滤再 join，利用分区裁剪，避免全表扫描。

## 五、星型 / 雪花（做报表模型时）

- 默认星型：事实表 + 维度表，join 少、报表好读。
- 只有同一维度层级被多个模型共享、且需要独立维护时，才拆雪花；否则把层级拍平在维度表里。
- 事实表先定粒度；维度用代理键（数仓生成的编号），事实表存编号。
- 需要看属性历史时保留版本行：`valid_from / valid_to / is_current`。
- 需要看表关系图时，用 Mermaid ER 图或 DBML，不要用流程图硬画表结构。

## 六、评审清单

- [ ] `b_` 是否一源一 CTE，没有 join/聚合？
- [ ] `f_`/`j_` 是否只在被复用或逻辑复杂时出现？
- [ ] 顺序是否按数据依赖，而不是按前缀？
- [ ] `a_` 是否一指标一粒度，列名/类型一致？
- [ ] 跨脚本复用的逻辑，是否已落 DWD/DWS？
- [ ] 单个 CTE 嵌套是否 ≤2 层，主干是否 ≤5 层？
- [ ] 多个 `a_` 是否重复扫描同一个 `b_`？
- [ ] 长表/宽表的选择是否有理由？
- [ ] `o_` 是否真的需要？

## 七、分层图：优先纯文本

评审时先画纯文本树。零依赖，聊天、终端、VS Code、Git diff 都能直接看：

```text
p_ 参数
├─ b_ 源表 A
│  └─ f_ 过滤/复用集
└─ b_ 源表 B
   └─ j_ join 结果
      ├─ a_ 指标 1
      └─ a_ 指标 2
         └─ 最终 SELECT / UNION ALL

依赖：a_ 指标 1 ← f_ 过滤集 + j_ join 结果
```

简单脚本直接写一行：

```text
p_ 参数 → b_ 源表 → a_ 指标 → 最终 SELECT
```

写法：

- 节点写 `层_业务名`，不要只写 `CTE1`；
- 树只画主依赖，跨分支依赖在树下面用"依赖："补一行；
- 节点超过 10 个，改成"层表 + 树"，不要硬画成一团；
- AgentBox 聊天不渲染 Mermaid，纯文本树可以直接看。

如果确实要图片，选不用装 Chrome 的方式：

| 方式 | 装 Chrome | 适合 |
|---|---|---|
| VS Code + Mermaid 扩展 | 否 | 评审时在编辑器里预览 |
| D2（单文件） | 否 | 直接导出 SVG/PNG |
| Graphviz（单文件） | 否 | 20+ 节点、复杂血缘 |
| draw.io / Excalidraw | 否 | 汇报美化，不适合评审产物 |
| mermaid-cli | 是（Puppeteer） | 仅 CI 或偶尔导出，日常不推荐 |

内部表结构不要贴到公网预览站。需要 Mermaid 源码时看 `references/mermaid-layering.md`。

## 反模式

- `b_` 里写 join/聚合；每个过滤都拆 `f_`；一个 `j_` 塞多表。
- 每个脚本都写 `o_`；CTE 嵌套 4 层；主干 8 层还不落表。
- 把同一段 `b_` 复制到多个脚本；跨脚本复用的口径各写各的。
- 20+ 个 `a_` 硬堆 `UNION ALL`，不评估扫描次数和长表/宽表。
- 用流程图硬画星型/雪花表结构。
