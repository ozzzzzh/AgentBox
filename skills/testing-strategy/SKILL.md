# 测试策略

## 何时使用

- 新增功能或修复 bug 前需要决定测什么、在哪一层测；
- 评审测试是否有效；
- 要在"声称完成"前做最小验证。

## 步骤

1. **先确定要保护的行为**：用一句话写出预期行为和不变量（输入 → 输出/状态）。没有明确行为的测试不要写。
2. **选最低有效层级**：
   - 纯逻辑、边界、校验 → 单元测试；
   - 跨模块契约、数据库/HTTP 集成 → 集成测试；
   - 关键用户路径、跨系统 → 少量端到端测试；
   - 不要为了覆盖率把同一行为在每一层重复测。
3. **修复 bug 先写失败测试**：用最小输入重现问题，确认在修复前失败、修复后通过；提交里保留该回归测试。
4. **覆盖边界与失败路径**：空值/空集合、上下限、重复提交、超时、错误分支、权限拒绝、并发竞争。
5. **测试行为而非实现**：断言可观察结果，不依赖私有方法或内部调用顺序；重构不应导致大量无关测试失败。
6. **保持确定性**：固定时间/时区/随机种子，隔离网络和文件系统；对外部依赖使用最小 stub，不要 mock 掉被测逻辑本身。
7. **运行最小相关验证**：改完先跑相关测试和类型检查，再跑更大范围；在结论中写明实际运行的命令与结果，未运行就说明原因。

## 反模式

- 只测 happy path；
- 用 `assert(true)` / 只断言不抛错；
- 一个测试覆盖十几个行为，失败时无法定位；
- 过度 mock 导致测试只验证 mock 的配置；
- 依赖真实网络、真实时钟或执行顺序；
- 覆盖率数字很高但关键错误路径缺失。

## 示例

```text
行为：同一批次重复执行两次，订单数不变。
测试：准备 3 条输入 → run(batch) → run(batch) → 断言行数仍为 3 且内容一致。
```

## 验证方式

- 新增/修复逻辑至少有一条会在旧实现上失败的测试；
- 关键失败路径有显式断言；
- 测试可重复运行，结果与顺序、时间、网络无关；
- 报告结论时附实际执行的测试命令与通过/失败数。
