# 错误处理与可观测性

## 何时使用

- 新增或修改可能失败的调用（网络、文件、数据库、解析、外部服务）；
- 排查"偶发失败但没有信息"的问题；
- 评审异常处理、日志、重试逻辑。

## 步骤

1. **区分错误类型**：可恢复（超时、限流、临时不可用、用户输入错误）与不可恢复（配置错误、数据损坏、程序 bug）。两类走不同路径，不要用同一个 catch。
2. **失败必须可见**：要么向上传播，要么记录并转换后返回；禁止空 catch 或"失败也返回空值"掩盖问题。
3. **在边界转换**：底层错误在模块边界转换为领域错误，附带上下文（操作、资源 id、重试次数），不要把原始 provider 错误直接暴露给上层或用户。
4. **日志**：
   - 结构化字段优于拼接字符串；
   - 记录操作、关键 id、结果、耗时；一次失败只记一次；
   - 不记录 token、密码、cookie、个人敏感数据；必要时脱敏后再记；
   - 用户可见消息与内部诊断信息分开。
5. **重试与超时**：只对幂等或明确可重试的操作重试；使用有上限的指数退避 + 抖动；每次调用都设超时；重试耗尽后返回明确错误。
6. **资源清理**：用 `finally` / `defer` / `using` 保证文件句柄、连接、锁、订阅、临时目录在成功和失败路径都释放。
7. **取消语义**：长任务要响应取消（AbortSignal / context / 中断标志），取消与失败区分开。

## 反模式

- `catch (e) {}` 或 `except: pass`；
- 用字符串包含判断错误类型；
- 重试无退避、无上限，或重试非幂等写操作造成重复；
- 把堆栈、SQL、内部路径直接返回给终端用户；
- 日志里打印完整请求体、token、PII；
- 超时只在最外层设置，内层调用可无限等待。

## 示例

```text
失败：POST /orders → 503
坏日志：  error: request failed
好日志：  op=create_order order=4821 attempt=2 elapsed_ms=3041
          error=upstream_unavailable retryable=true
用户提示：下单暂时失败，请稍后重试。（不包含上游地址和堆栈）
```

## 验证方式

- 为每个新增错误分支补测试：触发失败，断言返回类型/状态与日志字段；
- 确认日志中不含密钥和个人数据；
- 在有超时和取消的条件下跑一次，确认资源被释放、任务能及时退出。
