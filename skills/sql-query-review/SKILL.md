# SQL 查询与索引评审

## 何时使用

- 新增或修改查询、ORM 查询、报表 SQL；
- 排查慢查询、CPU/IO 飙升、连接池耗尽；
- 评审索引变更。

## 步骤

1. **拿到执行计划**：在接近生产的数据量下运行 `EXPLAIN (ANALYZE, BUFFERS)`（PostgreSQL）或 `EXPLAIN ANALYZE`（MySQL 8+）。没有计划就评审 SQL 只能算猜测，必须说明。
2. **检查访问路径**：是否存在全表/全索引扫描；扫描行数与返回行数的比例；join 顺序与连接算法是否合理；是否出现临时表、文件排序、hash join 溢出。
3. **核对索引匹配**：
   - 谓词列是否在索引前导位置，类型是否一致（隐式转换会让索引用不上）；
   - 排序/分组是否与索引顺序匹配；
   - 避免在索引列上套函数或做计算（改为范围条件或函数索引）；
   - 组合索引遵循最左前缀；区分度低的列不要单独建索引。
4. **消除 N+1**：循环内逐条查询改为批量 `IN` / join / 一次预取；注意 `IN` 列表大小上限。
5. **只取需要的列**：避免 `SELECT *`，尤其是大文本/JSON 列；分页用 keyset（`WHERE id > ? ORDER BY id LIMIT ?`）而不是大偏移 `OFFSET`。
6. **事务与锁**：
   - 事务尽量短，不在事务内做网络/文件 I/O；
   - 明确隔离级别；避免长事务持有锁；
   - 高并发更新用条件更新或行锁，按固定顺序加锁避免死锁；
   - 大批量写分批提交，评估锁等待和复制延迟。
7. **正确性**：检查 NULL 语义（`NOT IN` 遇 NULL）、重复行、聚合与 join 放大、时区、金额精度、排序是否稳定。

## 反模式

- 凭直觉加索引，不做计划分析；
- 对每列都建索引，拖慢写入；
- 用 `LIKE '%keyword%'` 做前缀不确定的大表搜索；
- 在循环里逐条查询数据库；
- 长事务里等待用户或调用外部服务；
- 用 `SELECT *` 再把大部分列丢掉；
- 声称已优化但没有前后计划或耗时对比。

## 验证方式

- 提供优化前后的执行计划与关键指标（扫描行数、耗时、buffer 命中）；
- 关键查询在目标数据量级下有可接受的上限；
- 索引变更有写入开销评估，并说明是否可在线创建；
- 结果集正确性通过对照查询或测试验证。
