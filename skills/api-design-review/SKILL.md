# API 契约设计评审

## 何时使用

- 新增或修改 HTTP/RPC 接口；
- 评审 OpenAPI/Proto/GraphQL schema；
- 判断接口变更是否向后兼容。

## 步骤

1. **明确资源与语义**：URL/RPC 方法表达资源或动作；动词落在 HTTP 方法上；同名概念在不同接口中命名一致。
2. **确定幂等与重试语义**：
   - `GET`/`PUT`/`DELETE` 幂等，`POST` 默认非幂等；
   - 创建、支付、扣减等非幂等操作用幂等键（Idempotency-Key）或客户端请求 id，并说明重复请求的返回；
   - 明确超时后客户端能否安全重试。
3. **契约与版本**：
   - 响应字段只增不删、语义不变；新增必填字段属于破坏性变更；
   - 破坏性变更走新版本或新端点，并给出迁移与下线时间；
   - 枚举值新增要考虑旧客户端行为（是否因未知值崩溃）。
4. **输入校验**：服务端校验必填、类型、长度、范围、格式；拒绝未知/过大字段；分页参数、过滤、排序有上限和默认值。
5. **授权与数据边界**：认证之外还要校验"这个用户能否访问这条资源"，不能只校验登录；租户/归属过滤在查询层强制；不在错误信息中泄露他人资源是否存在。
6. **错误契约**：统一错误结构（code / message / details / requestId）；状态码语义正确（400 参数、401 未认证、403 无权限、404 不存在、409 冲突、422 语义错误、429 限流、5xx 服务端）；5xx 不返回内部堆栈。
7. **稳定性**：分页用游标或稳定排序；限流与配额；超时；大响应分页或异步任务；明确最终一致性窗口。
8. **可观测性**：请求 id 贯穿日志；记录关键业务结果而非请求体；敏感字段脱敏。

## 反模式

- 用 `POST /getUser` 表达查询；
- 新增必填字段或修改字段含义却不升版本；
- 只校验登录不校验资源归属；
- 错误一律返回 200 + `{success:false}`；
- 无分页上限，允许一次拉全表；
- 返回内部异常、SQL 或上游地址；
- 幂等键缺失却声称"重试安全"。

## 验证方式

- 契约测试覆盖成功、参数错误、未认证、无权限、不存在、冲突；
- 兼容性检查：旧客户端针对新 schema 行为正确；
- 重复请求（同幂等键）返回一致结果且不产生重复副作用；
- 分页/过滤在大数据量下响应有界。
