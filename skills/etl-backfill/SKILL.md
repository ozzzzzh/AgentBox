# ETL 补数

## 什么时候用

- 跑批失败，分区数据不完整；
- 数据坏了，需要按原逻辑重做；
- 指标口径变了，要重算历史；
- 源表迟到、补发，需要更新旧日期；
- 新建模型，需要回补历史。

## 一、先判断补哪一类

| 类型 | 用哪版代码 | 做什么 |
|---|---|---|
| 跑失败/数据坏了 | 当时的代码 | 只补受影响分区，结果要和故障前一致 |
| 口径变了 | 新代码 | 重算历史，明确通知下游 |
| 源表迟到/补发 | 当前代码 | 只补实际变化范围，多取几天兜底 |
| 新建模型回溯 | 新代码 | 按任务依赖从上游往下补 |

"当时的代码"如果已经跑不了现在的表结构，不要硬跑：记录代码差异，按"口径变更/重述"处理，并通知下游。

## 二、补数前先圈范围

- 从对账差异、源表变更日志、失败分区列表，确定要补哪些日期。
- 不要默认全量；范围越小，风险越小。
- 列出上下游任务，按依赖顺序补：先上游，后下游。
- 提前通知下游和 BI：哪些表、哪些日期、大概多久。

日期范围通常来自：

- 调度失败记录里失败的分区；
- 源表 `updated_at` 超过上次更新时间的记录；
- 对账表里行数/金额有差异的日期。

## 三、一次只补一个分区

- 用 `WHERE dt = :dt`，一次一个分区；失败只重试这个分区。
- 不要 `WHERE dt BETWEEN ...` 一次全跑：中途失败难定位，也不好回滚。
- 每个分区要能重跑，结果一致：
  - 先 `DELETE` 当天分区，再 `INSERT`；
  - 或 `MERGE` / `UPSERT`；
  - Hive 用 `INSERT OVERWRITE ... PARTITION`。
- 支持分区交换的库，优先用分区交换，比逐行 `DELETE` 快。

```sql
-- 以 dt 分区为例
DELETE FROM fct_order WHERE dt = :dt;
INSERT INTO fct_order SELECT ... WHERE dt = :dt;
```

按引擎改写法：

- Hive/Spark：`INSERT OVERWRITE TABLE fct_order PARTITION (dt = :dt) SELECT ...`。
- Greenplum/PostgreSQL：先 `DELETE` 当天，再 `INSERT`。
- 支持分区交换的库：先建临时分区表，再交换分区，比逐行删除快。

执行顺序：备份 → 暂停下游 → 补上游 → 补下游 → 逐分区验收 → 恢复下游。

## 四、先备份，再替换

补数前保留上一版；对账通过再删，不通过就恢复。

```sql
-- 备份当天分区（备份允许 SELECT *）
CREATE TABLE fct_order_bak_20261125 AS
SELECT * FROM fct_order WHERE dt = '20261125';

-- 重算
DELETE FROM fct_order WHERE dt = '20261125';
INSERT INTO fct_order SELECT ... WHERE dt = '20261125';

-- 对账通过
DROP TABLE fct_order_bak_20261125;
-- 对账不通过
-- DELETE FROM fct_order WHERE dt = '20261125';
-- INSERT INTO fct_order SELECT * FROM fct_order_bak_20261125;
```

- 大分区备份占空间；空间不够时用分区交换或库的快照功能。
- 备份表名带日期，避免覆盖。

## 五、不要和日常任务撞车

- 同一个分区同一时间只能有一个任务在写，加锁或用状态表占位。
- 补数不要和日常调度同时跑同一张表。
- 限制并发，降低优先级，先保证日常任务。
- 下游任务先标记"待更新"，等上游补完再跑。

## 六、记录每个分区

每个分区记一行，事后才能回答"补了哪些天、用的哪版代码、谁操作的"。

```text
backfill_jobs(
  job_id, model, dt, code_version,
  operator, status, rows_affected, started_at, finished_at
)
```

没有调度平台的，用 CSV、工单或变更记录也行，至少写清：模型、日期、代码版本、操作人、结果。

## 七、每个分区单独验收

不要只看总量；总量对得上，可能只是两个分区互相抵消。

- 行数：和源表、上一版对比，差异要能解释。
- 金额/指标合计：和源表或旧结果对比，差异在约定范围内。
- 粒度唯一：例如 `category + plate` 不能重复。
- 空值率、0 值率：突然升高要查原因。
- 维度全集：该出现的板块/类型是否都在；缺的有没有补零。
- 抽样：挑几条明细和源表对一遍。
- 全部通过后再删备份。

```sql
-- 粒度重复检查，结果应为空
SELECT category, plate, count(*)
FROM fct_order
WHERE dt = :dt
GROUP BY 1, 2
HAVING count(*) > 1;
```

## 八、重述历史时通知下游

口径变更导致历史数据变化时，不能只改完就结束：

- 写清影响范围：哪些报表、接口、下游任务；
- 写清时间范围：从哪天到哪天；
- 写清原因：修复、口径变更、源表补发；
- 附新旧对比：行数、金额、关键指标差异；
- 写清生效时间，需要时冻结报表或双版本并行；
- 记入变更记录，方便下次追溯。

## 九、提交前检查

- [ ] 补数类型判断了吗？用旧代码还是新代码？
- [ ] 范围只包含受影响日期吗？
- [ ] 每个分区都能单独重跑吗？
- [ ] 有备份和回滚方案吗？
- [ ] 和日常调度互斥吗？
- [ ] 每个分区有任务记录吗？
- [ ] 行数、金额、粒度、空值、维度都验了吗？
- [ ] 下游和 BI 通知了吗？

## 反模式

- `BETWEEN` 一次全跑，失败后不知道补到哪。
- 不备份、不记录代码版本，出问题无法回滚。
- 修复和口径重述混着跑，历史数据来源说不清。
- 补数和日常调度同时写同一张表。
- 只看总行数/总金额，不逐分区验收。
- 改完历史不通知下游，报表口径对不上。
