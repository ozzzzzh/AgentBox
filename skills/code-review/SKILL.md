# 代码评审

## 何时使用

- 评审他人提交的 PR / diff；
- 提交前自审自己的改动；
- 判断一次改动能否合并、需要哪些补充验证。

## 步骤

1. **先确认范围与意图**：读 PR 描述和提交信息；确认 diff 只包含相关改动，没有夹带格式化、无关重构或生成文件。看不懂意图先问，不要靠猜。
2. **按三层顺序读，不要逐行漂移**：
   - 契约层：对外接口、数据模型、状态机、权限边界是否变化；
   - 控制流层：主路径之外的错误路径、空值、并发、重试、取消；
   - 细节层：命名、一致性、重复代码、注释。
3. **逐项检查**：
   - 正确性：边界输入、空集合、时区/编码、浮点与金额、整数溢出；
   - 错误处理：失败是否可见、是否被吞掉、是否泄露内部细节（见 `error-handling`）；
   - 并发与资源：共享状态、锁顺序、文件/连接/订阅是否释放；
   - 安全：输入校验、授权是否在服务端、密钥与 PII 是否入库或入日志；
   - 性能：新增循环内 I/O、N+1、无界集合、重复计算；
   - 可测试性：关键分支是否可测，是否补了覆盖 bug 的回归测试。
4. **对照项目规则**：检查 `CLAUDE.md` / `AGENTS.md` / 团队 Skill 中与该改动相关的约束，明确写出违反了哪一条。
5. **运行最小验证**：跑相关测试、类型检查或构建。无法运行时，明确说"未验证"及原因，不要假设通过。
6. **产出 finding**：按严重级别排序，每条包含位置、问题、触发条件、建议；不要堆无优先级的长评论。

## finding 写法

```text
[严重] src/orders.ts:142 — 并发取消会丢单
触发：两个取消请求同时到达时，status 读取与写入之间没有条件更新，
后到的请求把已退款订单改回 cancelled。
建议：改为带 status 条件的 UPDATE / 行锁，并补并发回归测试。
```

有效 finding 必须能回答：什么输入或状态、走到哪行、产生什么错误结果。只表达偏好（命名、风格）时标为 `建议`，不与 bug 混排。

## 反模式

- 只做风格和格式检查，忽略错误路径与并发；
- 把"我会这样写"当作缺陷，要求重写整个模块；
- 没运行验证就断言"应该没问题"；
- 一次抛出几十条同级别评论，淹没真正的高危问题；
- 评审超出 diff 范围的既有问题并阻塞本次合并（应另开 issue）。

## 验证方式

- 每条 [严重] finding 都能给出具体触发路径，或指向缺失的测试；
- 高风险的改动有对应的测试、类型检查或手动复现记录；
- 结论明确：可合并 / 需修改 / 需讨论，并列出阻塞项。
